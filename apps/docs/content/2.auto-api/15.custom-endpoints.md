# Custom Endpoints

@websideproject/nuxt-auto-api provides two approaches for building custom server endpoints that integrate with the auto-api pipeline: `createEndpoint()` for full pipeline integration, and standalone helpers for lightweight use in regular Nitro handlers.

## createEndpoint

`createEndpoint()` is the recommended way to build custom endpoints. It handles the full middleware pipeline, Zod validation, response formatting, and serialization.

### Resource-Bound Endpoint

When you specify a `resource`, the endpoint runs the auto-api pipeline before your handler: authentication, plugin
middleware, the permission check (undeclared = denied) and query validation. The handler holds only what the endpoint
does. Most endpoints need three lines of setup and no permission code:

```typescript
// server/api/posts/[id]/publish.post.ts
export default createEndpoint({
  resource: 'posts',
  scope: 'publish', // the permission: the person's and an API token's
  row: 'id',        // the row the route names, as ctx.row: missing or hidden 404, `objectLevel` 403
  refusal: 'Only editors publish posts.',

  handler: ctx => updateReturning(ctx.db, posts, ctx.row.id, { published: true }),
})
```

| Option | What it does for you | Default |
|---|---|---|
| [`scope`](#the-permission-scope) | Which permission authorizes the endpoint | The one its operation implies (the HTTP method) |
| [`row`](#the-row-row) | Loads the row the route names, by the resource's row rules | Your query, through the [row access helpers](#row-access) |
| [`refusal`](#the-refusal-refusal) | What a refused person is told | `Forbidden…` |

The request **body** is never checked against the resource's table schema (that describes a row, and a custom endpoint's
body is its own shape): declare `body` to validate it.

A query the handler writes itself is still yours to scope: `rowScope(ctx, 'posts', posts)` is the same visibility
as the list, as one SQL condition (see [row access](#row-access)).

**Responses are filtered like the generated routes'.** A resource-bound endpoint removes hidden fields
(`hiddenFields`, anywhere in the payload, nested objects included) and the fields the caller may not read
(`fields[x].read`, on the row or rows the handler returns) from its result. `findAuthorizedRow` and `ctx.db` give
whole rows, so a `passwordHash` the generated routes never show stays out of your response too. Set
`filterResponse: false` to return the payload untouched, or `filterResponse: true` on a standalone endpoint to
filter it against the registered resources' hidden fields. A `Response`, stream or `Blob` is never filtered.

Route params: `ctx.params` holds every segment of your file route — `ctx.params.slug` in `[slug].get.ts`, as
well as `id` and `relation`.

`createEndpoint` and every helper on this page are auto-imported in server code; they can also be imported from
`@websideproject/nuxt-auto-api/utils`.

### Standalone Endpoint

Without a `resource`, the caller is resolved (authentication and context extenders run, `ctx.user` /
`ctx.tenant` / `ctx.permissions` are set, `ctx.schema` holds every registered table) and plugin middleware runs —
but **nothing is authorized for you**. Gate it with `authorize`, or in the handler:

```typescript
// server/api/health.get.ts
export default createEndpoint({
  async handler(ctx) {
    return { status: 'ok', timestamp: new Date().toISOString() }
  },
  responseFormat: 'raw', // Don't wrap in { data }
})
```

### Body and Query Validation

Use Zod schemas for type-safe input validation:

```typescript
// server/api/users/invite.post.ts
import { z } from 'zod'
import { users } from '~~/server/database/schema'

export default createEndpoint({
  resource: 'users',
  operation: 'create',

  body: z.object({
    email: z.string().email(),
    role: z.enum(['user', 'editor', 'admin']).default('user'),
  }),

  query: z.object({
    sendEmail: z.stringbool().default(true), // 'false' → false (z.coerce.boolean would make it true)
  }),

  async handler(ctx) {
    // ctx.body and ctx.queryParams are typed
    const { email, role } = ctx.body
    const { sendEmail } = ctx.queryParams

    const [user] = await insertReturning(ctx.db, users, { email, role })

    if (sendEmail) {
      await sendInviteEmail(email) // your mailer
    }

    return user // hidden fields are removed for you
  },
})
```

### Response Format

Control how the response is wrapped:

```typescript
// 'auto' (default) - wraps in { data: result }
createEndpoint({
  responseFormat: 'auto',
  handler: async () => ({ name: 'Alice' }),
})
// Returns: { data: { name: 'Alice' } }

// 'raw' - passes through as-is
createEndpoint({
  responseFormat: 'raw',
  handler: async () => ({ name: 'Alice' }),
})
// Returns: { name: 'Alice' }

// 'raw' also sends a Response, stream or Blob unchanged
createEndpoint({
  responseFormat: 'raw',
  handler: async () => new Response(csv, { headers: { 'content-type': 'text/csv' } }),
})
```

### Transform

Transform the result before sending:

```typescript
createEndpoint({
  handler: async (ctx) => {
    return await ctx.db.query.users.findMany() // needs drizzle(…, { schema }); standalone, so nothing is authorized
  },
  transform: (users, ctx) => ({
    users,
    total: users.length,
    requestedBy: ctx.user?.email,
  }),
  responseFormat: 'auto',
})
// Returns: { data: { users: [...], total: 5, requestedBy: 'admin@example.com' } }
```

### Named gates (`endpointName`)

`endpointName` matches `authorization.custom[endpointName]` on the resource. Operations that gate declares are
decided by it — so one endpoint can open an operation the resource keeps closed (`create: false` on a resource
that exposes `/checkout`). Operations it does not declare fall back to the resource's own permissions.

```typescript
// resource auth: { permissions: { create: false }, custom: { checkout: { permissions: { create: 'member' } } } }
export default createEndpoint({
  resource: 'orders',
  operation: 'create',
  endpointName: 'checkout',
  handler: async (ctx) => { /* … */ },
})
```


### The permission (`scope`)

With no `scope`, an endpoint is authorized by the resource's rule for its operation, and the operation comes from the
HTTP method: a GET needs `read`, a POST `create`, a PUT or PATCH `update`, a DELETE `delete`. The method comes from the
file name (`stats.post.ts` only answers POST), so a caller can't pick a weaker one. Give every route file a method
suffix: a file without one answers every method.

`scope` says which permission the endpoint really needs. It applies to the person and to an API token alike:

```typescript
// A POST that only reads: a viewer and a read-only token (`*:read`) may call it.
createEndpoint({ resource: 'reports', scope: 'read', handler })

// An action of its own: the rule `permissions.publish` declares, else the held string `posts:publish`.
createEndpoint({ resource: 'posts', scope: 'publish', handler })

// A permission from outside the resource: a string with a colon names all of it.
createEndpoint({ resource: 'apiKeys', scope: 'workspace:settings', handler })

// No resource: the whole permission is the only form.
createEndpoint({ scope: 'reports:export', handler })
```

| `scope` | The person needs | An API token's scopes must cover |
|---|---|---|
| `read`, `create`, `update`, `delete` | The resource's rule for it (undeclared = denied) | `<resource>:<word>` |
| another word | `permissions[word]` if declared, else the held `<resource>:<word>` | `<resource>:<word>` |
| `some:permission` | The held `some:permission` | `some:permission` |

Held patterns count as everywhere: `posts:*` and `*` cover `posts:publish`. Declare a rule in `permissions` when
the string alone isn't the answer (a plan, a per-product grant):

```typescript
export const postsAuth: ResourceAuthConfig = {
  permissions: { read: true, update: 'posts:update', publish: ctx => ctx.user?.plan === 'team' },
}
```

In the playground (`/demo/recipes`): [`publish`](https://github.com/websideproject/nuxt-auto/blob/main/apps/playground/server/api/recipes/posts/%5Bid%5D/publish.post.ts) is an action of its own,
[`unpublish`](https://github.com/websideproject/nuxt-auto/blob/main/apps/playground/server/api/recipes/posts/%5Bid%5D/unpublish.post.ts) leaves the decision to the row rule,
[`search`](https://github.com/websideproject/nuxt-auto/blob/main/apps/playground/server/api/recipes/posts/search.post.ts) is a POST that only reads, and [`export`](https://github.com/websideproject/nuxt-auto/blob/main/apps/playground/server/api/recipes/export.get.ts) names a whole
permission with no resource.

![The playground's recipes page, signed in as the editor: post counts through rowScope, the publish, unpublish, search and export endpoints, duplicating posts with authorize, and the notes trash](/screenshots/api-recipes-1440.png)

A [named gate](#named-gates-endpointname) that declares the operation still decides first, and `skipAuthorization`
leaves only the token's check. A bare word with no `resource` has nothing to mean, so it fails at startup.

### The row (`row`)

`row` names the route parameter that holds a row of the resource. The row is loaded after the permission check, with
the answers of `GET /api/<resource>/:id`: missing or not visible (tenant, `listFilter`, soft delete) is a **404**, and
failing `objectLevel` is a **403**. The handler gets it as `ctx.row`, and `authorize` can read it too:

```typescript
// server/api/projects/[projectId]/archive.post.ts
export default createEndpoint({
  resource: 'projects',
  scope: 'archive',
  row: 'projectId',
  authorize: ctx => ctx.row.ownerId === ctx.user?.id, // anything the row rules can't say
  handler: ctx => updateReturning(ctx.db, projects, ctx.row.id, { archivedAt: new Date() }),
})
```

`objectLevel` runs with the endpoint's permission in `ctx.endpointScope`, so a rule that depends on what's being done
can tell: `ctx.endpointScope ?? ctx.operation`.

### The refusal (`refusal`)

What a signed-in person is told when the permission check, `row`'s `objectLevel` or `authorize` refuses them. A signed-out caller still gets
401 and `Authentication required`, and an error a rule throws itself keeps its own message:

```typescript
createEndpoint({
  resource: 'apiKeys',
  scope: 'workspace:settings',
  refusal: 'Only an admin or the workspace\'s owner can change who makes API keys.',
  handler,
})
```

### authorize

Runs after the pipeline and Zod validation, before the handler. Return `false` (or throw) to reject with 403:

```typescript
export default createEndpoint({
  resource: 'webhooks',
  row: 'id',
  authorize: ctx => ctx.row.userId === ctx.user?.id,
  handler: async (ctx) => { /* … */ },
})
```

In the playground: [`/api/recipes/posts/duplicate`](https://github.com/websideproject/nuxt-auto/blob/main/apps/playground/server/api/recipes/posts/duplicate.post.ts) refuses
unless every source post is readable (`findAuthorizedRows`), then writes the copies with `insertReturning`.

### Skip Authorization / Validation

Keep `skipAuthorization` for an endpoint that really has no permission: public ones (a newsletter sign-up, a webhook
checked by its signature). Everything else reads better as a `scope`.

```typescript
createEndpoint({
  resource: 'users',
  skipAuthorization: true, // the permission check does not run; a `scope` still binds an API token
  skipValidation: true, // skip the resource's QUERY validation (bodies are only checked against your own `body`)
  handler: async (ctx) => { /* ... */ },
})
```

## Row access

For the one row a route names, use [`row`](#the-row-row). For anything else, the generated routes load rows through
these helpers; use them in custom endpoints to get the same answers:

| Helper | What it does |
|---|---|
| `findAuthorizedRow(ctx, resource, id, { softDeleted? })` | One row by primary key. Invisible or missing → **404**; fails `objectLevel` → **403** |
| `findAuthorizedRows(ctx, resource, ids)` | The subset of `ids` the caller may see |
| `rowScope(ctx, resource, table, { softDeleted? })` | The SQL condition (tenant + `listFilter` + soft delete) for your own queries; `undefined` when nothing applies |
| `passesObjectLevel(ctx, resource, row)` | Run the resource's `objectLevel` on a row |
| `assertResourcePermission(resource, op, ctx, { recordId? })` | 401/403 unless the caller holds `op` on any registered resource |
| `checkPermission(op, authConfig, ctx)` / `getAuthConfig(ctx, resource)` | Boolean permission check against a resource's effective config |
| `await readableColumns(ctx, resource, table)` / `hiddenFieldsOf(ctx, resource)` | Columns the caller may read (async) / hidden columns |
| `filterHiddenFields(rows, ctx)` / `await filterReadableFields(rows, ctx)` | Strip hidden fields / fields the caller may not read from what you return |
| `protectedFieldsFor(ctx, resource, table, 'create' \| 'update')` + `stripProtectedFields(data, set)` | Drop server-owned columns (soft delete, audit, tenant, pk) from client input |
| `tenantWriteField(ctx, resource, table)` | The tenant column to stamp on writes, if any |
| `insertReturning(db, table, values)` / `updateReturning(db, table, id, set)` | Insert/update and return the rows on every dialect (MySQL has no `RETURNING`) |

`softDeleted` is `'exclude'` (default), `'include'` or `'only'`.

```typescript
// server/api/posts/recent.get.ts
import { and, desc, gte } from 'drizzle-orm'
import { posts } from '~~/server/database/schema'

export default createEndpoint({
  resource: 'posts',
  operation: 'list',
  async handler(ctx) {
    const since = new Date(Date.now() - 7 * 86_400_000)
    const scope = rowScope(ctx, 'posts', posts)
    return ctx.db.select().from(posts)
      .where(and(gte(posts.createdAt, since), scope))
      .orderBy(desc(posts.createdAt))
      .limit(20)
  },
})
```

When you apply `rowScope` yourself, the resource's `objectLevel` (a per-row function) is not part of the SQL —
filter with `passesObjectLevel` if the resource has one.

In the playground: [`/api/recipes/post-stats`](https://github.com/websideproject/nuxt-auto/blob/main/apps/playground/server/api/recipes/post-stats.get.ts) counts published and
draft posts within `rowScope`.

## Standalone Helpers

For regular Nitro event handlers where you don't need the full pipeline, use the standalone helpers:

### getAutoApiContext

Resolve the caller (authentication + context extenders) in a plain Nitro handler. Like a standalone
`createEndpoint`, it authorizes nothing. Pass `{ resource }` so the permission and row-access helpers read that
resource's config:

```typescript
// server/api/dashboard.get.ts
import { count } from 'drizzle-orm'
import { posts, users } from '~~/server/database/schema'

export default defineEventHandler(async (event) => {
  const ctx = await getAutoApiContext(event)
  if (!ctx.user) throw createError({ statusCode: 401 })

  const userCount = await ctx.db.select({ count: count() }).from(users)
  const postCount = await ctx.db.select({ count: count() }).from(posts)

  return respondWith({
    users: userCount[0].count,
    posts: postCount[0].count,
  })
})
```

### validateBody / validateQuery

Validate request input with Zod and get typed results:

```typescript
// server/api/contact.post.ts
import { z } from 'zod'

const ContactSchema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
  message: z.string().min(10),
})

export default defineEventHandler(async (event) => {
  const body = await validateBody(event, ContactSchema)
  // body is typed as { name: string, email: string, message: string }

  await sendContactEmail(body) // your mailer
  return respondWith({ sent: true })
})
```

### respondWith / respondWithList / respondWithError

Standardized response formatting with serialization:

```typescript
// Single item → { data: { id: 1, name: 'Alice', createdAt: '2025-01-01T00:00:00.000Z' } }
return respondWith(user)

// List with metadata → { data: [...], meta: { total: 100, page: 1, limit: 20 } }
return respondWithList(rows, { total: 100, page: 1, limit: 20 })

// Error (throws) → 404 / 422 with `data.details`
respondWithError(404, 'User not found')
respondWithError(422, 'Validation failed', { field: 'email', message: 'Already taken' })
```

### getDb

Quick access to the database and adapter:

```typescript
export default defineEventHandler(async (event) => {
  const { db, adapter } = getDb()

  // All-or-nothing on every engine — a transaction, or one db.batch() on D1
  await atomicWrites([
    tx => tx.insert(orders).values(orderData),
    tx => tx.insert(orderItems).values(itemsData),
  ], adapter)

  return respondWith({ success: true })
})
```

`adapter.atomic(fn)` is a real transaction everywhere except D1, where it runs `fn` directly (see
[Database Adapters](/auto-api/database-adapters#atomic-writes-on-every-engine-d1-included)).

## All Available Helpers

| Helper | Description |
|--------|------------|
| `createEndpoint(options)` | Full pipeline endpoint with Zod validation |
| `getAutoApiContext(event, { resource?, operation? })` | Caller context (user, tenant, permissions, db, schema) for plain handlers — authorizes nothing |
| `validateBody(event, zodSchema)` | Validate request body, throw 400 on failure |
| `validateQuery(event, zodSchema)` | Validate query params, throw 400 on failure |
| `respondWith(data)` | Wrap in `{ data }` with serialization |
| `respondWithList(data, meta?)` | Wrap in `{ data, meta }` with serialization |
| `respondWithError(status, message, details?)` | Throw standardized error |
| `getDb()` | Get `{ db, adapter }` |
| `await getResourceSchema(name)` | Get table schema from registry |
| `await getRegistry()` | Get full resource registry |
| `serialize(data)` | Serialize dates to ISO strings |
| `filterHidden(data, ctx)` | Alias of `filterHiddenFields`: remove the resource's hidden fields |

See [Row access](#row-access) for the authorization helpers.

## Migration from defineAutoApiHandler

`defineAutoApiHandler` was removed; `execute` becomes `handler`, and the handler returns the payload (the
`{ data }` wrapper is added for you). See [Upgrading](/auto-api/upgrading).
