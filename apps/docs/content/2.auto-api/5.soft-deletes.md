# Soft Deletes

Soft deletes mark records as deleted (a timestamp) instead of removing them, with restore, purge,
cascade-to-children, and batch (cascade-group) restore/purge.

## Enabling it

Use the [`softDelete()` schema preset](./17.schema-presets) — one import turns the whole pipeline on:

```typescript
import { sqliteTable, text } from 'drizzle-orm/sqlite-core'
import { id, timestamps, softDelete } from '@websideproject/nuxt-auto-api/schema/sqlite'

const sd = softDelete()
export const posts = sqliteTable('posts', {
  ...id(),
  title: text('title').notNull(),
  ...timestamps(),
  ...sd.columns,            // deletedAt, deletedBy, deletionId, deletedReason
}, t => [...sd.indexes(t)]) // posts_trash_idx + posts_batch_idx
```

### Detection (and the `deleted_at` collision)

A table is soft-deletable when it has a `deletedAt`/`deleted_at`/`deletedDate` marker that is **nullable**,
**or** carries a preset companion column (`deletionId`/`deletedReason`/`deletedBy`). A **NOT NULL**
`deleted_at` with no companions is treated as a *domain* column, **not** soft-delete (so tables like a
GDPR erasure log that store "when the subject was erased" are not mistaken for soft-deletable).

Disable per-resource with `autoApi.authorization.<resource>.softDelete: false` (or a `string[]` allow-list).

## Lifecycle columns

| Column | Meaning |
|---|---|
| `deletedAt` | marker — `NULL` = live, timestamp = trashed |
| `deletedBy` | userId who trashed (stamped from the request) |
| `deletionId` | batch id stamped on the row **and all cascaded children** |
| `deletedReason` | optional reason (`?reason=`) |

## Behaviour

- **Delete** `DELETE /api/posts/123` → soft delete (stamps the columns + cascades). `?force=true` →
  permanent purge (needs the `purge` permission). Returns `{ success, softDeleted, deletionId }`.
- **List/Aggregate** hide trashed rows by default. `?includeDeleted=true` (live + trashed) and
  `?onlyDeleted=true` (trash only) require permission to view deleted (see below).
- **Get/Update** on a trashed row return 404 unless the caller may view deleted; editing a trashed row
  is blocked (restore it first).

## Permissions (configurable, like every other action)

`restore`, `purge` and `viewDeleted` are first-class permission keys, resolved through the same engine
as `read`/`create`/`update`/`delete` — so a string role, a `string[]`, a function, or an **entitlement
gate descriptor** (evaluated by the registered evaluator chain) all work.

```typescript
autoApi: {
  authorization: {
    posts: {
      permissions: {
        update: 'editor',
        restore: 'editor',          // who can restore
        purge: 'admin',             // who can permanently delete
        viewDeleted: 'editor',      // who can see trash
        // or a gate descriptor handled by your entitlement evaluator:
        // restore: { gate: 'trash:restore' },
      },
      // Equivalent alternative home (permissions.* wins if both set):
      softDelete: { restore: 'editor', purge: 'admin', viewDeleted: 'editor', cascade: 'auto', retentionDays: 30 },
    },
  },
}
```

**Resolution order**

- restore → `permissions.restore` → `softDelete.restore` → `permissions.update` → `'admin'`
- purge → `permissions.purge` → `softDelete.purge` → `permissions.delete` → `'admin'`
- viewDeleted → `permissions.viewDeleted` / `softDelete.viewDeleted` → else global admin **or** org admin/owner

Defaults are safe: with no config, restore/purge require `admin` (never fail-open).

## Restore & purge

```typescript
POST   /api/posts/123/restore          // restore one row (and its cascade batch, if any)
DELETE /api/posts/123?force=true       // purge one row (needs `purge`)
```

## Cascade & batch

Soft-deleting a parent mirrors each FK's `onDelete`, reversibly:

- `cascade` → soft-delete soft-deletable children (recursively), stamped with the **same `deletionId`**;
  non-soft-deletable cascade children are left for the DB's real `ON DELETE CASCADE` at purge time.
- `set null` → null the child FK.
- `restrict` / `no action` → the delete is blocked with **409** (a pre-flight runs before any row is
  mutated, so nothing is half-deleted). Disable cascade with `softDelete.cascade: 'off'`.

Act on the whole cascade group via the **batch endpoints** (from `@websideproject/module-auto-softdelete`):

```typescript
POST /api/softdelete/batches/:deletionId/restore   // restore every row in the batch
POST /api/softdelete/batches/:deletionId/purge     // purge every row in the batch
```

Each batch endpoint enforces the per-resource `restore`/`purge` permission for every affected resource.
The `useTrash()` composable + `/admin/trash` page use these.

## Retention

`@websideproject/module-auto-softdelete` ships a daily `softdelete:purge` task that hard-deletes trash
older than `retentionDays` (per-resource override via `softDelete.retentionDays`; `0` = never).

## GDPR

Privacy erasure writes raw Drizzle and bypasses the soft-delete handler, so it still hard-deletes /
anonymizes trashed rows — soft delete never shields PII from erasure. Revision snapshots taken on
delete are subject to the revision module's GDPR connector.
